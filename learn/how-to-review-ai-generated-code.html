How to review AI-generated code: a risk-tiered checklist

Coding agents produce code that looks finished and fails in places a skim misses. AI-Native Engineering

Short answer

To review AI-generated code well, stop reading it like code from a colleague. Check the spec and the agent’s plan before the diff, let automation clear the mechanical problems (build, tests, security scans, new dependencies) before a person opens the pull request, then spend human attention on the places AI-written code fails most: invented APIs and packages, missing or inverted permission checks, tests that only restate the implementation, changes outside the ticket and drift from your conventions. Scale the depth of review to the risk of the change, and send it back to the spec when the spec was the problem.

This guide gives you a catalog of how AI-written code fails, a split between what to automate and what a person must read, a copy-paste checklist for low, medium and high-risk pull requests, a way to review the tests an agent wrote, and a pull request template for AI-authored changes. It assumes a team using GitHub Copilot, Cursor, Claude Code or a similar agent, with pull requests as the place code gets accepted.

How AI-written code fails differently

Code from a coding agent compiles, reads cleanly and usually matches the request on the happy path. Its mistakes sit in places a skim does not catch, and they are different from the mistakes a tired colleague makes. Two published studies show the pattern.

  • In Veracode’s 2025 GenAI Code Security Report (July 2025), more than 100 language models completed 80 curated coding tasks, and in 45% of test cases they introduced a vulnerability in the OWASP Top 10. Models failed to defend against cross-site scripting (CWE-80) in 86% of relevant cases and log injection (CWE-117) in 88%. Veracode also found that larger models did not perform significantly better than smaller ones on security.
  • In a study presented at USENIX Security 2025, researchers generated 576,000 code samples with 16 popular models and found that, on average, at least 5.2% of the packages suggested by commercial models and 21.7% of those suggested by open-source models did not exist. They counted 205,474 unique hallucinated package names. An attacker who registers one of those names gets their code installed by anyone who trusts the suggestion.

Veracode’s November 2025 update reported that most providers’ newer models still scored in the 50-59% range on its security tests, with OpenAI’s GPT-5 reasoning models the exception at 70-72%. The tools improve, but not fast enough to skip review.

The AI code failure catalog

These are the failure patterns to look for. The right-hand column says whether a machine can catch it reliably or whether it needs a person.

FailureWhat it looks like in a diffWho catches it
Invented packagesA new dependency with a plausible name that is not on the registry, or was published last week by an unknown accountAutomation: a dependency check on every lockfile change
Invented or outdated APIsA call to a method your library version does not have, or a deprecated signature copied from older code the model sawMostly automation (type check, build); a person for dynamic languages and config
Missing or inverted permission checksAn endpoint without the authorization decorator its neighbors have, a ! dropped from a role check, a tenant filter left off a queryA person, with a security scan as a backstop
Unsafe input and output handlingUser input reaching HTML, SQL, shell commands or log lines without the encoding your codebase uses elsewhereSAST catches common cases; a person checks the ones your scanner has no rule for
Tests that mirror the implementationTests written from the code rather than the requirement, so they assert whatever the code does, including its bugsA person; mutation testing helps
Scope creepA “small fix” that also refactors a shared module, renames a function across 30 files or edits CI configAutomation flags paths outside the ticket; a person decides
Convention driftA second HTTP client, a new date library, error handling that swallows exceptions where your code re-raises them, a helper that duplicates one you already haveArchitecture rules in CI catch the written ones; a person catches the rest
Confident wrong logicAn off-by-one in pagination, time zones ignored, a retry loop without a limit, a cache that never expiresA person reading against the acceptance criteria

The pattern behind the list: AI-written code fails where the correct answer depends on context the model did not have. Your authorization model, your conventions and your edge cases live in your codebase and your team’s heads, not in the prompt.

What to automate before a person reviews

A reviewer’s attention is the scarce resource. Nothing a machine can check reliably should reach a person unchecked. Make these checks required on the branch, so a pull request that fails them never asks for a human review.

Where an AI reviewer fits

An AI reviewer is a useful first reader and a poor last one. As of November 2026, GitHub’s documentation for Copilot code review says that by default Copilot leaves a “Comment” review, not an approval, so its reviews do not count toward required approvals; approvals are off by default and can be turned on at the enterprise, organization or repository level. GitHub’s own concept page says Copilot is not guaranteed to spot every problem, tells you to supplement its feedback with a human review, and lists dependency management files such as package.json among the files it does not review. That last point matters: the invented-package problem has to be caught by a dependency check, not by the AI reviewer.

Copilot code review reads repository instructions from .github/copilot-instructions.md, path-specific .github/instructions/**/*.instructions.md files and an AGENTS.md file, so the conventions your agents write against can be the same ones your AI reviewer checks against (GitHub Docs). Keep one source of truth for conventions and point every tool at it.

The risk-tiered review checklist

Not every AI-written pull request needs the same review. A test-only change and a change to your sign-in flow carry very different risk, and applying the strictest checklist to both trains reviewers to skim. Assign the tier from what the change touches, not from how big it is or who wrote it: a twelve-line migration can be riskier than a thousand lines of generated client code.

Low

Read the diff against the ticket

Documentation, copy, test-only changes, isolated UI and config with no runtime effect. One reviewer, focused on scope and conventions.

Medium

Read the plan, then the diff

Feature code, business logic, internal APIs and non-breaking schema additions. One reviewer who knows the area reads the spec and plan first.

High

Two people, one of them the owner

Authentication, authorization, payments, personal data, migrations, public APIs, infrastructure and CI/CD. The code owner approves, and someone runs it.

On GitHub, a ruleset can enforce the high tier: requiring review from code owners means a pull request that modifies content with a code owner must be approved by that owner before it merges, and requiring approval of the most recent reviewable push means someone other than the last person to push has to approve the final version (GitHub Docs, available rules for rulesets). Put your high-risk paths in CODEOWNERS and those two rules do most of the enforcement for you.

The copy-paste checklist

Paste this into your review guide or a saved reply. The tier definitions are a starting point; adjust the path lists to your own system.

## AI-authored PR review: LOW risk
Docs, copy, tests only, isolated UI, config with no runtime effect
- [ ] Automated checks green (build, tests, lint, SAST, secrets)
- [ ] Diff matches the ticket; no files outside its scope
- [ ] No new dependencies
- [ ] Skim for convention drift (naming, helpers we already have)

## AI-authored PR review: MEDIUM risk
New feature code, business logic, internal APIs, non-breaking schema additions
- [ ] Everything in LOW
- [ ] Spec and agent plan read BEFORE the diff; diff follows the plan
- [ ] Every acceptance criterion maps to code and to a test
- [ ] Tests assert behavior from the spec, not values copied from the code
- [ ] Error paths: failures raise or return the way our code does, nothing swallowed
- [ ] Inputs validated and outputs encoded at every boundary the change touches
- [ ] Every called method and library version exists in our lockfile
- [ ] New dependency (if any) approved by its owner and pinned
- [ ] Logging carries no personal data, secrets or raw user input

## AI-authored PR review: HIGH risk
Authentication, authorization, payments, personal data, migrations,
public APIs, infrastructure, CI/CD and the review policy itself
- [ ] Everything in MEDIUM
- [ ] Two human approvals, one from the code owner of the area
- [ ] Authorization checked on every new or changed entry point, including the negative case
- [ ] Queries scoped to the right tenant or user
- [ ] Migration is reversible or has a written rollback; tested on production-sized data
- [ ] Public contract changes are backward compatible or versioned
- [ ] Behind a feature flag, with the metrics to watch named in the PR
- [ ] Reviewer has run the change locally or in a preview environment

Notice what the checklist does not ask: whether the code is elegant, or whether you would have written it the same way. With an agent, rewriting is cheap. Spend review time on whether the change is correct and safe, and push style preferences into lint rules and agent instructions where they apply to every future change.

Reviewing the tests AI wrote

The tests an agent writes alongside its code are the weakest evidence in the pull request. When the same model writes the code and the tests from the same understanding, the tests confirm that understanding, including where it is wrong. A green test suite tells you the code does what the agent thought it should do. Your job is to check that against what the spec says it should do.

  1. Read the test names before the test bodies. Each acceptance criterion in the spec should have at least one test you can find by name. Missing criteria are the gaps; extra tests for behavior nobody asked for are scope creep.

  2. Look for expected values copied from the output. An assertion like expect(total).toBe(1047.3) with no explanation often means the agent ran the code and pasted the result. Expected values should come from the requirement or a worked example.

  3. Check what is mocked. A test that mocks the function it claims to test, or mocks the database in a test about a query, proves nothing. Mocks belong at the boundaries you do not own.

  4. Find the negative cases. For anything touching permissions or input, there should be a test where the wrong user is refused and bad input is rejected. Agents write the happy path first and often stop there.

  5. Watch for weakened tests. Deleted assertions, new skip or xfail markers, loosened tolerances and regenerated snapshots are how an agent makes a failing test pass. Any change to an existing test needs a reason in the pull request.

  6. Break the code on purpose. Flip a condition or delete a line in the new code and run the tests. If they still pass, they are not testing that line. Mutation testing tools such as Stryker, PIT and mutmut automate this for a changed file.

A practical rule: for medium and high-risk changes, at least one test should be written or rewritten by a person, or by an agent from the acceptance criteria alone before it sees the implementation. That gives you one source of evidence that does not share the code’s blind spots.

A pull request template for AI-authored changes

A good pull request template moves the questions a reviewer would otherwise have to ask into the description, before review starts. For AI-authored changes it also records how the change was made, which helps the reviewer and leaves a record for later. Save this as .github/pull_request_template.md (or your platform’s equivalent) and make the template-completeness check blocking.

## What and why
Ticket / spec: <link>
One paragraph: what this changes and why.

## How it was made
- Agent and model: <e.g. Claude Code, Copilot agent, Cursor>
- Plan: <link to the approved plan, or paste it>
- Written by a person: <files or "none">
- Tests written from the acceptance criteria before the code: yes / no

## Risk tier
- [ ] Low   - docs, copy, tests, isolated UI, inert config
- [ ] Medium - feature code, business logic, internal APIs
- [ ] High  - auth, payments, personal data, migrations, public APIs, infra, CI
Why this tier: <one line>

## Scope
Files outside the plan: <list, or "none">
New dependencies: <name, version, why, owner who approved, or "none">
Existing tests changed or deleted: <list with reason, or "none">

## How to verify
Steps a reviewer can run, and what they should see.
Metrics to watch after release (high tier): <list>

The “How it was made” block is not there to single out AI work for suspicion. It tells the reviewer where to look: a plan to compare against, which parts a person wrote, and whether any test was written independently of the code. The “Scope” block surfaces the three things agents do quietly: touch files outside the plan, add dependencies and change existing tests.

Review the spec and plan before the diff

The cheapest place to catch a wrong change is before it is written. If the spec is vague, the agent fills the gaps with plausible guesses, and the reviewer then has to reverse-engineer those guesses from a diff. A two-minute read of the spec and the agent’s plan (files to touch, interfaces, migrations, tests) tells you what the diff should contain. Then the review becomes a comparison, which is faster and more reliable than reading cold.

This is why a governed delivery process puts a person at the plan, not only at the pull request. In Upcore’s AI-native engineering pipeline, AI drafts an implementation plan covering files, interfaces, data migrations and tests, and an architect approves the plan before any build starts.

When to send it back instead of fixing it

Reviewers fixing an agent’s pull request line by line is a sign the problem is upstream. Send it back, and say where it should go back to.

What you seeSend it back toWhy
The change does something reasonable that the ticket did not ask for, or misses a case nobody wrote downThe specThe agent guessed. Fix the acceptance criteria and regenerate, or the next change guesses the same way
The structure is wrong: logic in the wrong layer, a new pattern where an existing one fitsThe planComments on the diff will not move the design; a corrected plan will
Correct logic, but it breaks a convention the team agreedThe agent instructionsWrite the rule into your instructions file or an architecture check so it holds for every future change
More than a few hundred lines, or several unrelated changesThe author, to splitLarge diffs get skimmed. Smaller pull requests get read
Tests were weakened or deleted to passThe author, with the failing test restoredThe failing test was the evidence; removing it hides the bug
A small, local mistake in otherwise sound workNowhere: fix it in reviewA suggested change is faster than another cycle

Track where pull requests get sent back. If most go back to the spec, invest in spec templates. If most go back for convention drift, your agent instructions and architecture checks are the gap. That record turns review from a gate into feedback that improves the next batch of changes, which is the idea behind AI-native engineering.

Where this fits in a governed delivery process

Everything above can be done with the tools you already have: a ruleset, a CODEOWNERS file, a pull request template, a dependency check and a review guide. Teams usually struggle with the parts around the review: specs good enough for an agent to follow, architecture rules written down as checks, risk scoring that decides which pull requests a person must read, and a record of every decision.

AI coding tools write the code; they do not decide what is safe to merge. Our comparison of AI-native engineering and AI coding tools covers where each stops. Questions

Common questions.

Should AI-generated code be reviewed differently from human code?

The standard is the same: correct, safe and maintainable. The emphasis differs. AI-written code rarely has typos or obvious sloppiness, so reviewers who scan for those miss its real problems: invented dependencies, missing authorization, tests that restate the code and changes outside the ticket. Point attention there, and let automation handle the mechanical checks first.

Can an AI reviewer replace a human reviewer?

Not for anything that matters. An AI reviewer is a good first reader for readability issues and obvious bugs, and it is fast. It lacks your context: the authorization model, conventions nobody wrote down and what the customer asked for. GitHub’s own Copilot documentation tells teams to supplement Copilot’s feedback with a human review.

How do I catch hallucinated packages?

Automate it rather than relying on reviewers. Run a check on every lockfile change that confirms each new package exists on the registry, flags packages published recently or with little usage history, and compares against an allowlist. Route any new dependency to a named owner for approval, and pin versions so a later upload cannot change what gets installed.

Should pull requests disclose that AI wrote them?

Yes, as a matter of process rather than blame. Recording the agent, the plan it followed and which parts a person wrote tells the reviewer what to compare against and where independent evidence exists. It also gives you data later: which kinds of changes agents handle well, and where review keeps finding the same problems.

How long should reviewing an AI pull request take?

It depends on the tier, not the line count. A low-risk change with green checks can take minutes. A high-risk change deserves the time it takes to read the plan, check every entry point and run it. If reviews of medium-risk changes routinely take longer than writing the spec would have, the specs are probably too thin.
